## 2026-07-15: Phase 0 — runtime build without a Metal toolchain, validation, smoke test

**The runtime problem.** This machine (M4 Max, 64 GB, macOS 26.3) has Xcode 26.3 but not its Metal Toolchain component (Xcode 26 split it out). `xcodebuild -downloadComponent MetalToolchain` fails on a stale-support-frameworks plug-in error; the prescribed `xcodebuild -runFirstLaunch` repair hangs waiting for an admin authorization dialog (23 min at 0 CPU, killed). No PrismML wheels exist anywhere (PyPI empty for easymlx/prism*; GitHub release v0.0.1-prism has no assets; docs.prismml.com says build from source). Direct MobileAsset download via Apple's Pallas service (gdmf.apple.com) failed (asset audience for MetalToolchain not discoverable without admin/dyld-cache tools).

**Solution: hybrid build (patched).** Two facts make it possible: (a) with `MLX_METAL_JIT=ON`, all fork-touched kernels (quantized incl. 1-bit, steel gemm, scan, ...) are embedded as source and compiled by the *runtime* Metal compiler (always present); (b) the only kernels always compiled offline are a small base set (arg_reduce, conv, gemv, layer_norm, random, rms_norm, rope, sdpa, spec_decode, fence) — and a full fork-vs-v0.31.2 diff audit shows none of their host↔kernel ABIs changed in the fork (`random.metal`'s ulong→uint is kernel-side only, host identical, and the stock pairing is the original consistent one; `spec_decode` is fork-new and only reachable via speculative decoding, which we never use; NAX kernels are M5-only, this is an M4). So: take `mlx.metallib` from the stock **mlx-metal 0.31.2** wheel (macosx_26 build) for the base set, JIT everything else from fork sources. Second obstacle: `make_compiled_preamble.sh` uses `xcrun metal -E -H` just to enumerate quote-includes; replaced with a 40-line pure-python include walker (verified: headers with zero quote-includes and no conditional includes anywhere in the kernels tree). Patches in `patches/mlx-prism-no-metal-toolchain.patch` (+ `scripts/jit_preamble_deps.py`); build wired into uv via `[tool.uv.sources] mlx = {path="vendor/mlx", editable=true}` + `no-build-isolation-package`, `CMAKE_ARGS="-DMLX_METAL_JIT=ON -DMLX_PREBUILT_METALLIB=..."` (see scripts/setup_env.sh). mlx-lm pinned to **0.31.2** (PrismML's own pin; 0.31.3 requires mlx>=0.31.2 final, and the fork's version `0.31.2.dev20260715+10b5fe4` sorts below it in PEP 440). Build time ~75 s (no offline kernel compilation). The clean path (if we ever get admin): `sudo xcodebuild -runFirstLaunch && xcodebuild -downloadComponent MetalToolchain`, then rebuild without CMAKE_ARGS.

**Validation** (`experiments/runtime_validation/validate_runtime.py`, all PASS): GPU==CPU for every borrowed-metallib kernel (random exact; rms_norm/layer_norm/rope/sdpa/gemv/conv within fp tolerance; arg_reduce exact); 1-bit dequantize == independent numpy unpack, bit-exact, both devices; 1-bit quantized_matmul == dequant-then-matmul (CPU exact, GPU max|d| 1.8e-4); real Bonsai q_proj tensor: mx.dequantize == numpy unpack bit-exact and dequant values exactly ±s_g. One nuance: GPU-vs-CPU `mx.quantize` (bits=1) breaks exact-midpoint ties differently (identical scales/biases and reconstruction error; codes differ on a few elements) — benign, we never mx.quantize model weights. Fork test suites: test_quantized.py 29/29, test_random.py 14/14, test_fast_sdpa.py 15/15 (1 skip).

**Census key numbers** (census_Bonsai-27B-mlx-1bit.{json,md}): backbone 24.73B logical params / 4.21 GB deployed (matches whitepaper "MLX 1-bit 4.21 GB"); embed+lm_head+final-norm tail 2.58B / 0.40 GB; vision tower 0.92 GB / 333 tensors. Blocks are size-uniform within type: each linear-attention block ≈ 389.3M params / 60.0 MB; each full-attention block ≈ 378.1M / 58.2 MB. So **one dropped block ≈ 58–60 MB and ~1.5% of backbone compute**; KV-cache bytes are only saved when full-attention blocks (3, 7, ..., 63) are dropped.

**Smoke test** (`experiments/smoke/smoke_test.py`, thinking mode, temp 0.7 / top-p 0.95 / top-k 20): 200 tokens generated, coherent structured reasoning. **Decode 70.1 tok/s, peak memory 4.66 GB** (53-token prompt). With a 1,460-token prompt: **prefill 230–262 tok/s, decode 66–70 tok/s, peak 6.74 GB** (first-run prompt_tps at tiny prompts is meaningless — it absorbs one-time JIT kernel compilation). Reference: whitepaper M4 Pro GGUF tg128 26 tok/s; M4 Max has ~2× the bandwidth, and this is the MLX path, so ~70 tok/s is plausible and a pleasant surprise — mini-bench runtime estimates should use ~66 tok/s, not 26.

**Decisions.**
- Stock mlx-lm handles the architecture; PrismML's mlx fork (patched as above) supplies the kernels. No easymlx package exists; the whitepaper's "easymlx" is evidently the demo-repo + fork combination.
- Vision tower stays in the shipped file (mlx-lm drops it at load; zero RAM cost); stripping is deferred to release packaging of folded packs.
- No MTP/DSpark tensors in the MLX pack → nothing to disable locally; keep spec-decode off in any serving config regardless.
- Ternary 2-bit mapping verified remotely without downloading the 8.5 GB pack (HTTP range reads).

## 2026-07-15: Phase 1 proposal (block-influence mapping) — implementation stops here pending review

**What Phase 0 changes about the plan.** Nothing structural. Two positive updates: (1) throughput is ~2.5× better than budgeted (66–70 tok/s decode vs the 26 planned on), so KL screens and mini-bench are cheaper than feared; (2) both models coexist trivially (4.66 GB peak each at short context). One risk retired: per-layer heterogeneous bits (for the promotion merge) is structurally fine — MLX stores quantization per-tensor in config and the fork dispatches per-tensor bits; a toy heterogeneous load should still be verified in Phase 3 week 1. One new wrinkle: the runtime is a locally patched fork build — validated, but any future `uv sync` without CMAKE_ARGS rebuilds it identically (patch is deterministic), and validate_runtime.py should be re-run after every rebuild (add to habit).

**Design: redundancy map of the 1-bit model.**

*Harness.* No monkeypatching: `model.language_model.model.layers` is a plain Python list; wrap each block in a thin recorder that forwards `__call__` and accumulates streaming statistics per block (no activation storage): sum of cos(h_in, h_out) per token, sum of angular distance arccos(cos)/π, sum of relative update magnitude ‖Δ‖/‖h_in‖, token count; plus for same-type near-adjacent pairs (j − i ∈ {1,2,3}, gap allowed) sum of cos(Δ_i, Δ_j) computed on the same forward pass (Δ = h_out − h_in at each block's own input — this is the quantity the merge operators approximate). All stats are mx scalars evaluated once per sequence; memory footprint negligible.

*Calibration set* (frozen once, committed as token id lists): 64 sequences, ~2K tokens each — 24 on-policy reasoning (MATH-500 prompts, completions generated by the unfolded 1-bit model in thinking mode, then frozen); 16 long-context prose (public-domain/wikitext chunks); 12 code (permissively licensed source files); 12 instruction/chat transcripts. Teacher-forced prefill only. Runtime estimate: 64 × 2K tokens at ~240 tok/s prefill ≈ 9 min per model — cheap enough to re-run under seed/composition ablations.

*Outputs* to `experiments/block_influence/`: per-block JSON (BI mean/median/p10/p90, angular variant, ‖Δ‖/‖h‖, per-source-category breakdown), pairwise same-type similarity matrix for the merge shortlist, and a markdown summary with the ranked drop candidates — the first redundancy map of an end-to-end 1-bit LLM.

*Immediately after the map (still Phase 1):* single-block-drop KL screen on the top ~8 candidates to calibrate the map against ground truth and test Gate A. Drop mechanics: copy config + delete the block from the layer list (never touching surviving tensors), load both models, teacher-force the frozen on-policy set, mean full-vocab forward KL. Both models in memory ≈ 10 GB — fine. Gate A: if no single-block drop achieves on-policy KL < 0.05 nats (provisional; whitepaper's 4-bit-KV noise floor is 0.0009), 1-bit has near-zero structural slack → document as the finding, promote ternary.

**Discovery that changes Phase 2 (verified in mlx-lm 0.31.2 source):** `qwen3_5.py` never reads `config.layer_types`. Block type is positional: `DecoderLayer.is_linear = (layer_idx + 1) % full_attention_interval != 0`, and the mask/cache wiring assumes position 0 is linear and position `interval-1` is full attention. **Consequence: "delete blocks from the layer list + reload via stock mlx-lm" only works for drop patterns aligned to whole groups of 4.** Any other pattern (including all single-block drops and the H5 only-linear vs with-full ablations) silently instantiates wrong block types. The Phase 2 drop harness therefore needs a small loader shim — subclass or monkeypatch `Qwen3_5TextModel`/`DecoderLayer` to build block types from an explicit `layer_types` list (falling back to the interval rule), before any folded pack is loaded. This is runtime-construction code, not weight modification; surviving weights stay byte-identical (PackReader.read_raw exists for the byte-identity verification). Recorded in the census markdown as well. Added Phase 1 question 6: the same shim should be built and toy-tested (e.g., reload the unfolded model through it and confirm identical logits) BEFORE the Phase 1 single-block-drop KL screens, since those screens are the first consumer of non-aligned drops.

## 2026-07-19: Decision/idea from Thanasis — position folds as smaller models, benchmark against the size class they enter
